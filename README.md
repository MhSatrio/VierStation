# VierStation

Scientific research workspace by VierApparatus: **Airtable-style relational databases + bioinformatics integrations + background automation + project management.**
Workflow it is built around: **DNA → Gene → Protein → Chemical → Structure → Analysis → Research project.**

## Run it

Requires Node ≥ 24 (uses the built-in `node:sqlite` and native TypeScript; the server has **zero runtime dependencies**).

```bash
npm install
npm run build        # production client (Vite)
npm start            # http://127.0.0.1:8787  – API + built client, data in ./data
```
Development: `npm run dev:server` and `npm run dev:client` (Vite proxies `/api`). Copy `.env.example` to `.env` for options (contact e-mail for NCBI, optional NCBI key, start-offline switch, …).
There is **no account or login** (see *Local, offline-first* below): the first start opens straight into a local workspace that already contains **“My first project”** with the full pipeline tables, views and (switched-off) automations. Data folder: `./data` (`VIERSTATION_DATA_DIR`).

Docker: `docker build -t vierstation . && docker run -p 127.0.0.1:8787:8787 -v vs-data:/app/data vierstation` (Dockerfile provided; not built in the authoring environment – see Known limitations).

## What is in it

| Area | Implementation |
|---|---|
| Relational engine | SQLite (WAL). Real `links` table (not text fields), inverse fields, per-link evidence metadata. 19 field types incl. formula (own sandboxed parser + GC/REVCOMP/TRANSLATE/MW), lookup, rollup, sequence, structure, status, user, attachment. |
| Views | Grid (virtualized, inline edit, keyboard), Kanban (drag = status update), Gallery, List, Calendar, Relationship explorer (Cytoscape, below). All views read the same records; saved views keep filter / sort / group / hidden fields / widths. Live sync through server-sent events. |
| Integrations | NCBI E-utilities + BLAST, UniProt, AlphaFold DB, PubChem, ChEMBL, BindingDB, RCSB PDB (REST/search/GraphQL), InterPro. Per-host rate limits, retries with `Retry-After`, SQLite response cache. |
| Discovery | DNA→gene (GenBank annotation first, BLAST similarity second), gene→proteins **incl. isoforms**, protein→chemicals (ChEMBL mechanisms + measured activities, PDB co-crystal ligands, BindingDB), structures (AlphaFold lookup + PDB), PubChem enrichment, duplicate detection/merge by InChIKey/CID/ChEMBL ID. |
| Scientific integrity | Every link stores relation type, evidence text, source DB, reference URL and an **evidence class** (experimentally verified / database annotated / computationally predicted / sequence inferred / user supplied / unverified). Predictions are never shown as confirmation; sequences are classified coding / non-coding / partial / uncertain with the *basis* (annotation vs inference). Per-record provenance history. |
| Structures | Pre-calculated only – no folding is ever launched. 3D viewer (3Dmol, lazy-loaded): representations, pLDDT / chain / residue colouring, residue highlight, picking, PDB download, pLDDT plot, PAE image. |
| Jobs | Durable SQLite queue: retries with back-off, rate-limit delays, cancellation, dedupe keys, crash recovery, per-job log, real progress counts only (no invented percentages). CPU analyses run in `worker_threads`. |
| Automations | Trigger → conditions → actions with templates; loop prevention (self-trigger blocked, chains stop at depth 3), duplicate prevention, manual re-run, run history. |
| Notifications | In-app + live push (SSE), optional browser notifications, per-event preferences, deadline reminders. No e-mail is ever sent. |
| Analysis | Pairwise (affine-gap global/local, BLOSUM62) and star multiple alignment, k-mer/identity comparison, NJ/UPGMA trees, heatmaps with clustering, PCA, descriptive stats, correlations, Welch t-test. **Export to Python / R / Julia** with the exact data and parameters, plus CSV/JSON. |
| Security | Local-only server (loopback bind, Host allow-list), CSRF header, input validation, upload sniffing (no HTML/SVG), CSV-injection guard, CSP + security headers, rate limits, AES-256-GCM secrets (never sent to the browser), audit log. |

## Local, offline-first – no accounts

VierStation runs on **your computer**. There is **no sign-up, login, password, e-mail verification or cloud account**; the first start opens straight into a local workspace that already contains “My first project”. Projects made with the earlier account-based version stay accessible (they are adopted by the single local workspace identity; its name is only used in the activity log).

* **Offline-first, not offline-only.** The local SQLite database is the source of truth. Offline you can open projects, browse and edit records and relationships, read cached NCBI/UniProt/PubChem answers, view saved structures and images, run local analyses (alignment, trees, statistics) and export. Anything that needs a scientific database (NCBI, UniProt, AlphaFold, PubChem, ChEMBL, BindingDB, RCSB, publications) **waits in the job queue** with the visible message “Waiting for an internet connection…”, is never dropped or failed silently, and runs when the connection returns. Stale cached answers are served rather than nothing, and say so. The **Network chip** in the header (also *Settings → Network & offline*) shows online / offline / “working offline” (a switch that stops all outbound calls) and how many tasks are waiting.
* **Safety of the data.** *Settings → Local data & backups*: automatic backups (the newest 20 are kept), manual backup, restore (a safety copy of the current data is taken first and put back automatically if the restore fails), **whole-workspace export** to one `.vsws` file (database + files + images + structures) and import into another installation (validated and integrity-checked; refused while background tasks are running). Clearing caches never touches your records.
* **Security without a login.** The server binds to `127.0.0.1` by default, refuses requests whose `Host` header is not a localhost form (DNS-rebinding guard; `VIERSTATION_ALLOWED_HOSTS` for deliberate exceptions), still requires the `X-VS` header on every change (CSRF), and prints a warning if you make it listen on a network address – **do not expose it to a network you do not trust**. API keys are encrypted at rest and never sent to the browser. Docker: publish the port to localhost only (`-p 127.0.0.1:8787:8787`).
* **Settings kept:** appearance/theme, defaults, NCBI contact e-mail and API key, network/offline preferences, local database management, cache, import/export, in-app/browser notification preferences, tooltips, activity log, software information. Removed: sign-up, login/logout, password recovery, verification, members, Brevo e-mail.

## Relationship Explorer, reactions and pathways

Open **Explorer** in the sidebar, a record’s **Relationships** section, or a table’s **Relationships** view. It is a working relationship and biochemical workspace, not only a picture: every node is a real record and every line is a stored relationship, a field link, a reaction role or a pathway step.

* **Graph (Cytoscape.js 3.30, MIT, lazy-loaded chunk ≈ 130 KB gzip).** Pan/zoom, drag nodes, multi-select (Shift / box), layouts (force-directed, concentric, hierarchy, circle, grid), search by name, filters by entity type, relationship type, **evidence**, tag, organism, source database, verification and pathway (applied *before* drawing), hide/show a category from the legend, double-click or **“Show N more connections”** for lazy expansion (a double border marks nodes with unloaded connections), **Explore related network** with depth 1–4, reset view, keyboard (arrows move between records, Enter expands). Export: Cytoscape JSON, GraphML, CSV (with evidence), VierStation JSON, PNG, and a **saved view** file that re-opens with the same filters, expansions and node positions. A node cap (default 400, up to 3,000) with an explicit “Showing N records” notice keeps big networks fast; **Table** mode lists *all* relationships page by page.
* **Blue-only visual system (brand #4570B6 / #CAEBFB and darker/lighter blues).** *Shape + a marker letter* tell the entity type (DNA, RNA, gene, protein, enzyme, chemical, metabolite, reaction, pathway, organism, publication, structure); *line style, width and the evidence word written on the line* tell the evidence (solid = experimental / annotated / literature / user, **dashed = computationally predicted, dotted = unverified**); selection = thick border + pale-blue halo; pathways are dark-blue outlined containers. Colour is never the only signal. Contrast is tested (`tests/explorer-ui.test.ts`): marker text ≥ 4.5 : 1 on every node fill, node borders ≥ 4.3 : 1 and edge lines ≥ 3.3 : 1 against the white canvas (the test caught two failing fills, gene and organism, which were corrected). A legend is always shown.
* **Inspector** (no leaving the graph): source (manual / external database / VierStation-generated, with accession links to UniProt, PubChem, NCBI Gene, RCSB, DOI, PubMed), key fields, structure image, relationships with evidence, pathways, tags, citations and provenance. A database annotation is **never** shown as experimentally verified.
* **Two ways to create relationships, one stored record.** (A) *Connect* mode: drag from one node onto another → a panel asks for type, evidence, description and citations → nothing is saved until **Save** (cancellable; an optional *quick connect* for graphs of ≤ 60 nodes stores “Associated with / unverified”). (B) The record’s **+ Add relation**: “(this record) is related to (record) as (type)”, several rows, “Add another relationship”, save all or one by one, with DOI/PMID/accession/UniProt/PubChem/URL/publication-record citations and tags; records can be found or created on the spot (find-or-create by name, so “glucose” is never duplicated). Both call `POST /api/relationships` (equivalence is checked in the browser tests).
* **Relationship model.** Many-to-many in its own table (`relationships`: source, target, type, direction, description, evidence class, verification, organism, conditions, source DB/accession, origin, timestamps, local creator, citations, tags). The same pair can have several relationships with different meaning or evidence; exact duplicates are refused with a clear message; deleting a relationship never deletes its records. 19 built-in types (binds to, inhibits, activates, substrate of, product of, converted into, catalyzed by, encodes, expressed by, regulates, interacts with, associated with, located in, part of pathway, cytotoxic to, coagulant / antimicrobial / antioxidant activity, cited in) plus **custom types** (name, reverse wording, description, directional, usual source/target kinds, default line style); an unusual combination asks for confirmation and is still allowed. Legacy field links from discovery appear read-only and can be **converted** into full relationships.
* **Reactions are records** with reactants, products, enzymes/catalysts, cofactors, inhibitors, activators, regulators (roles), stoichiometry, reversibility (irreversible → / reversible ⇌ / unknown ⇢), organism, compartment, conditions, evidence, citations and tags. **Pathways are ordered collections of reactions**: the order exists only if a curated source or you defined it (next / alternative links, branches and cycles allowed); otherwise the pathway says **“Order unknown / uncertain”** and is shown as an unordered set – VierStation never infers order from shared chemicals or tags. One chemical or reaction record can belong to many pathways without being duplicated; starting / intermediate / final chemicals are derived from the reactants and products inside the pathway. Views: network, **pathway** (container; vertical flow for long pathways), **flow** (process cards) and **table** – the same records.
* **Images.** Chemicals: PubChem 2-D depiction by CID, else InChIKey, else SMILES – **never by name**. Proteins: a backbone image *drawn here from real coordinates* of an experimental PDB file (preferred) or the AlphaFold model, labelled experimental vs **computationally predicted**. Cached on disk with source, identifier and date; not re-fetched; “Refresh” re-fetches; a miss is remembered for 24 h and explained instead of showing a made-up picture. A **Structure image** column (thumbnail → larger viewer) exists in the Proteins and Chemicals tables and is added automatically to older projects.
* **Tooltips** explain relationship types, evidence classes, reaction roles, pathway order states, filters and graph controls (hover, keyboard focus, tap).
* **Try it:** `npm start`, then `npm run seed:example` loads a glycolysis-style example (42 records, 8 reactions, 2 pathways – one ordered with a branch, one with unknown order; mixed evidence). It is illustrative data, not a curated database; running it twice duplicates nothing.

**Measured (this machine, Node 24, Chromium via Playwright).** Server, 9,000 relationships / 4,500 records: neighbourhood 15–16 ms, depth-3 expansion 33–45 ms, global view (500) 106–125 ms, facets and relationship pages < 800 ms. Browser, 4,012 relationships / 1,519 records: first draw of the bounded 818-node view 0.85–1.4 s, 30 zoom steps 1.1–1.3 s, a focused neighbourhood < 80 nodes, table mode pages 50 rows. *The earlier custom graph was re-tested first:* its table graph silently drew only the neighbourhoods of the **first 60 records** (600 chemicals → 180 nodes) while reporting `truncated: false`, showed only legacy field links (no typed relationships, no evidence filter, no tags), recomputed an O(n²) layout in React state on every frame, lost positions on every refresh, and clicking a node navigated away. It stayed smooth (≈ 52 fps) at that small size. It was replaced rather than patched.

## Sequence Lab – DNA identification, alignment & phylogenetics

Open it from the sidebar (**Sequence Lab**), from a DNA record (**Open in Sequence Lab**), or import reads there. One workspace per sequence with the sections *Overview · Raw sequence · Quality inspection · Cleaning · NCBI matches · Related species · Outgroups · Alignment · Phylogenetic tree · Final identification · Workflow history · Exports*. The steps are guided but not rigid: any section can be used in any order and repeated; a repeat creates a **new** result and keeps the old one.

**Transparency model (what makes every step traceable)**

* The raw sequence is stored once and is **immutable at the database level** (SQLite triggers reject UPDATE/DELETE). Cleaning creates new *versions* (with a position map back to the raw read); undo/redo/revert add history, they never rewrite it.
* Every operation is a row in the per-record **operation log**: step, parameters, input/output versions, tool, database + retrieval time, who did it, whether it was automatic, warnings, status (running → completed / failed / cancelled), and what it supersedes. The UI history, the **Markdown change log** and the **exported code** are all generated from that log – nothing is written by hand.
* The DNA record’s **Sequence** and **Length** fields always show the current *working* version (so grids, analyses and discovery use the cleaned sequence); the raw read stays in the lab. The first import adds five metadata columns to the DNA table (Sample ID, Marker / gene, Read type, Source file, Imported at).
* Quality scores and chromatogram peaks exist only for AB1/FASTQ input. For FASTA/pasted input they are not shown and quality trimming is refused, never faked. Records that existed before the lab get a raw version from the sequence they hold *now*, and the log says so.

| Step | What it does | How it was verified |
|---|---|---|
| Import | Paste, FASTA, FASTQ (Phred+33/+64), AB1 (own ABIF parser), or an existing record | AB1 parser output identical to Biopython on a real 3730 trace; FASTQ/AB1 round-trips |
| Quality | Length, GC, Q20/Q30, ambiguity, homopolymers, low-quality windows, **chromatogram viewer** (4 traces, per-base quality, second-peak flags), suggestions that are never auto-applied | Real AB1 file in browser test; ratio logic unit-tested |
| Cleaning | Sliding-window and modified-Mott trim, ambiguous-end trim, keep/remove region, remove bases, edit base / IUPAC code, mask low quality, mark uncertain, reverse-complement, **merge with the reverse read** (overlap alignment + column-wise consensus: an N / ambiguity code opposite a real base takes the real base, two real bases are decided by Phred quality when it clearly differs, otherwise an IUPAC code; the result is **one new record** named “Merged: <forward> (id) + <reverse> (id)” – or a name you give – whose history stores both inputs; the forward and reverse records stay unchanged in the DNA table and are listed under the merged sequence in the Sequence Lab; **Open from DNA table…** and **Merge forward + reverse…** pick records from the table), raw-vs-clean diff, undo/redo/revert | Python re-implementation of every operation executed against the stored versions (hashes match) |
| NCBI BLAST | megablast/blastn, database choice, E-value, hit list, optional Entrez restriction; table with **identity and query coverage as separate columns**, mismatches, gaps, E-value, bit score, strand; filters; five explained sort orders; query/subject alignment view; selection | Parser on synthetic JSON2; **live run against real NCBI** (see below) |
| Related species | Rule-based choice from BLAST hits: one per species (strains merged via NCBI taxonomy), uncultured / environmental / placeholder names (“… sp.”, “… bacterium”) excluded, genus cap, identical sequences removed; optional **genus search** (a taxon-restricted BLAST inside the best match’s genus) brings in species the top hits never reach; the *aligned region* of each record is fetched in the query’s orientation (minus-strand handled); every inclusion/exclusion has a recorded reason; manual add by accession (auto reverse-complement); **species typed by name** (NCBI Taxonomy lookup → BLAST of *your* sequence restricted to that taxon → aligned region of the best named hit; retries NCBI server errors and never reports an unreachable NCBI as “name not found”) | Synthetic dataset with known truth incl. a minus-strand record; **live runs against real NCBI** |
| Outgroups | Assistant derives the ingroup clade from real NCBI lineage ranks (lowest rank shared by ≥ 60% of the ingroup), runs a taxon-restricted BLAST in the sister lineage (`txidA[Organism:exp] NOT txidB[Organism:exp] …`, ingroup genera excluded), widens the clade once if fewer than 3 are found, proposes ≤ 5 (one per genus, ≤ 2 per family), and **rejects candidates as similar to the query as the ingroup** (these are ingroup members or mislabeled GenBank entries – seen in real data); explains each, says honestly when fewer than 5 exist; nothing is added without your click | Synthetic (incl. a mislabeled look-alike) + live |
| Alignment | Built-in **progressive** (k-mer guide tree, profile–profile affine-gap DP) and **iterative refinement** (leave-one-out, kept only if the sum-of-pairs score rises); pairwise global/local; manual gap editing stored as a separate step that cannot change residues | Invariants (residues intact, no all-gap columns), SP-score monotonicity, 2-sequence optimum equals the pairwise aligner; Biopython `PairwiseAligner` gives identical scores |
| Trees | NJ, UPGMA, minimum evolution, maximum parsimony, maximum likelihood (JC69/K80/F81/HKY85 ± Γ); p/JC69/K2P/TN93 (± Γ) distances; pairwise/complete/partial gap deletion; seeded bootstrap in parallel workers; outgroup/midpoint/no rooting; AIC/BIC | Likelihood checked against brute-force enumeration; simulation recovers the true topology; NJ topology reproduced by Biopython |
| Tree viewer | Rectangular, cladogram and circular layouts, zoom/pan, collapse/expand clades, clade highlight, support colouring, scale bar, SVG/PNG/Newick export | Browser test |
| Interpretation | Plain-language reading (closest clade, support, outgroup monophyly, nearest relatives) with a limitations list; **never** states an identity | Unit + browser test |
| Final identification | Evidence summary (BLAST identity *and* coverage, tree reading) and **your** recorded conclusion + confidence; "fetch full NCBI record" shows a preview (features, references, what will/won’t be saved) and saves only after confirmation | Preview leaves the log untouched (tested) |
| Exports | **PDF report** (own zero-dependency PDF writer; real Jost font and VierApparatus icon embedded; summary, quality, cleaning/merge, BLAST, references with reasons, alignment, tree, limitations, identification, history, reproducibility – steps not run are stated as not run); tree as SVG; Markdown change log from the stored log; Python workflow script (whole workflow or any single step) with an explicit *exact / partial* reproducibility statement and notes; FASTA (raw, working, dataset, alignment), Newick, JSON history. No API keys in any export | Scripts executed in Python in tests |

**Tooltips** are an app-wide, dependency-free component (`src/ui/Tip.tsx`, wording in one dictionary `src/ui/help.ts`): hover after 0.5 s, keyboard focus (immediate), tap on the (i) button for touch, Esc / blur / outside tap to dismiss, `role="tooltip"` with `aria-describedby` set while shown. Used on parameters, metrics and terms in the lab, and on evidence classes, discovery buttons and analysis settings elsewhere.


**Live validation (real NCBI, 2026-11-05, `npm run live:lab`).** The whole pipeline passed on a human mitochondrial COI fragment (601 bp): BLAST `core_nt` (38 s) → top hit *Homo sapiens*, 100 % identity over 100 % of the query; relatives *H. sapiens* + *H. heidelbergensis* (genus search); outgroup *Pan paniscus* (90.4 %; the assistant widened Hominidae → Primates and reported that fewer than five existed); 4 × 601 alignment; NJ tree with 100 bootstraps rooted on the outgroup; interpretation “groups with *Homo sapiens* with strong bootstrap support (100 %) – consistent with, but does not prove, that identity”; Markdown + script exported. Running it against real data also exposed problems that the synthetic tests could not, all fixed and covered by tests: top-100 BLAST lists dominated by one species and by placeholder names (“marine bacterium”); strains of one species counted separately; **GenBank records labelled as other genera whose sequences were identical to the query** (they would have been chosen as “best” outgroups); NCBI answering some valid E-utilities terms with HTTP 500 (`sort=relevance`, `[Accession]`); a taxon-restricted BLAST reported as “0 sequences searched” (now repeated once as a fresh search); BLAST result coordinates running backwards (`hit_from > hit_to`) on the minus strand; and a **rate-limit slot leak** (a cancelled request waiting for the BLAST host’s one-at-a-time limit blocked every later BLAST until restart). 16S fragments of *E. coli*, *B. subtilis* and *S. aureus* were also tried: the relatives were 99.5–100 % identical in the region, the alignment had 0–4 variable sites, and the tree step **refused** to build a meaningless tree – the marker simply cannot separate those species, which is what the tool should say.

**Keeping BLAST hits and mapping where samples come from.** Tick hits in the BLAST table and **Save to the DNA table** (aligned region or whole record): each becomes a real DNA record with its GenBank collection information and, when GenBank states them, `/lat_lon` and `/geo_loc_name`. The DNA table gets the columns *Collection location, Latitude, Longitude, Location precision, Location source*. **Sample map** (sidebar, “Show map” on the DNA table, “Show map” in a Lab record) draws a rotatable globe without any map library or tile server (outlines: Natural Earth, public domain); the pin colour is the **precision** of the place – dark navy = exact/specific, VierApparatus blue = city, near-white = only the country is known (pin at the country centre) – with a dashed uncertainty ring. Place names are resolved offline for bare countries and otherwise through OpenStreetMap Nominatim (1 request/s, cached, © OpenStreetMap contributors); precision comes from what Nominatim matched, a name nobody finds stays off the map, and coordinates typed by a person are never overwritten. Verified with synthetic NCBI/Nominatim (`tests/geo.test.ts`, browser test); **not yet run against the live Nominatim** in the automated tests.

**Documentation.** `docs/VierStation_Documentation.docx` (≈ 50 pages): how the system works, a “which file do I edit?” table, a licence and originality audit, step-by-step case studies, troubleshooting and appendices (every file, every API route). Sources to rebuild it: `docs/build-sources/`.

**One-command run (`npm run identify`).** `scripts/identify.ts` drives the same code through the whole chain – forward read → clean → (reverse read → merge) → BLAST → related species → species typed by name → outgroups → alignment → tree – against the real NCBI and writes the workflow script (`*_workflow.py`), PDF report, tree (Newick, SVG, PNG when Chromium is installed), alignment/dataset FASTA, Markdown change log and full JSON history. It uses its **own data folder** (`<out>/data`), so your VierStation database is untouched; `VIERSTATION_DATA_DIR=<out>/data npm start` opens the run in the app (`<out>/OPEN-THIS-RUN.txt` says how; there is no login).

```
npm run identify -- --forward fwd.fasta --reverse rev.fasta --species "Trichoderma harzianum, Trichoderma viride" --outgroup-species "Fusarium oxysporum" --out runs/sample1
```

**Live run on a real, poor read (2026-11-05, `runs/user-forward-read/`).** A 653 bp forward read with 26.5 % N (longest N-free stretch 24 bp): `blastn` found only a 140 bp window (22.7 % of the read) matching *Trichoderma*/*Hypocreales* ITS–rDNA records at 69.7 % identity (E ≈ 4·10⁻¹⁰; every N counts as a mismatch). Four species typed by name were collected (*T. harzianum*, *T. viride*, *T. reesei*, *T. atroviride*); a typed outgroup (*Fusarium oxysporum*) was refused because only 13.6 % of the read aligned; the outgroup assistant found none. The resulting tree has 15 variable and **0 parsimony-informative** sites, and the report says so (*inconclusive*). The run also exposed two defects, now fixed and tested: NCBI’s taxonomy search answered valid names with HTTP 500 and this was wrongly reported as “name not found”, and placeholder names such as “fungal endophyte” were accepted as relatives.

**What exports can and cannot reproduce.** Cleaning, pairwise alignment and NJ/UPGMA trees are reproduced exactly (Python/Biopython; verified by executing the exports). BLAST/Entrez steps are re-queried with the recorded parameters – NCBI databases change, so results can differ later (stated in the script). The built-in aligner, ME/MP/ML and the bootstrap RNG have no exact outside equivalent; the script embeds the stored alignment/Newick and names the closest alternative (MAFFT/MUSCLE, IQ-TREE, Biopython parsimony, FastME). No R or Julia export exists for the lab.

## Architecture decisions (and why)

* **New app, reusing the brand and toolchain.** The website (`../vierapparatus`) is the visual guideline (real `icon.svg`, tokens, Jost). VierCRM’s IndexedDB single-table store could not provide relations, server jobs or secret keys, so only its stack (React 19 + Vite + TS) and ideas were reused. Next.js was rejected: a SPA + long-running job server needs neither SSR nor serverless limits.
* **Zero-dependency server on Node 24.** `node:sqlite` (SQLite 3.51 with FTS5), `node:test`, native type stripping: nothing to compile, nothing to patch. Client dependencies: React, Jost, 3Dmol (lazy).
* **3D viewer chosen by measurement (gzip):** 3Dmol 157 KB · NGL 358 KB · Mol\* 1,509 KB. 3Dmol is lazy-loaded (only when a viewer is opened).
* **No Rust/WASM/C++.** Sequence and statistics code is pure TypeScript and measured fast enough (below); native code would add a build chain for no measured gain. The place it would pay off first is the O(n·m) alignment kernel for sequences > 10 kb – flagged, not built.
* **One canonical filter/sort implementation** (`shared/filters.ts`) over a bounded in-memory row cache; the SQL fast path handles the unfiltered grid. FTS5 rowid = record rowid (a full-table `DELETE … WHERE rid=?` was found quadratic by the benchmark and replaced: 225 → 4,500+ inserts/s).

* `npm run bench` – the benchmark above.

## Known limitations (honest list)

* **Sequence Lab limits.** Built-in aligner/tree engines are textbook implementations, **not** MAFFT/MUSCLE/IQ-TREE/MEGA/BioEdit/CLC equivalents and are slower and less accurate on large (> ~40 sequences) or very divergent data. No GTR model, no automatic model selection (AIC/BIC are reported for the model you chose). Maximum-parsimony branch lengths come from one most-parsimonious reconstruction, minimum-evolution negative lengths are shown as 0, UPGMA output is rooted by construction. ML bootstrap uses a fast mode (model parameters fixed, ≤ 2 NNI rounds per replicate). Trees are limited to 80 sequences, alignments to 80.
* **Forward + reverse merge, species by name and the PDF report** (added after the first release): the merge is verified on *simulated* read pairs (known truth, Ns, conflicts, wrong orientation, unrelated reads) and its Python port is executed against the stored hashes – it has **not** been run on a real read pair. A read with ≈ 25 % N carries little information on its own (the BLAST page now warns, pre-selects blastn with E-value 10, and explains a zero-hit result with a one-click sensitive re-run): BLAST counts each N as a mismatch and no 28-mer seed exists (use blastn, which `npm run identify` chooses automatically), and a tree built from a short aligned window can have almost no informative sites – the interpretation then says *inconclusive*. Species-by-name takes the best taxon-restricted BLAST hit, which is not necessarily type material, and needs the marker to be deposited for that taxon. The PDF was validated with PyMuPDF and fontTools, not Acrobat/Preview; text is limited to the glyphs Jost has (a few symbols such as ≥ are written as >=).
* **External aligners** (MAFFT, MUSCLE, Clustal Omega) can be selected when they are on the server’s PATH; the adapter is tested only with stand-in programs, **never against the real tools** (none installed here).
* **BLAST databases** offered are `core_nt`, `nt` and `refseq_rna` (verified live). The specialised marker databases (e.g. `16S_ribosomal_RNA`) were tried and never completed in testing, so they are not offered; restrict by Entrez query instead. NCBI queue time varies (38 s – many minutes); the job waits 8 min, retries once, and can be cancelled.
* Lab exports: Python only (no R/Julia). The Markdown change log reflects what VierStation stored; for records adopted from before the lab it says the raw sequence is the stored one, not necessarily the original file.
* **R and Julia exports were not executed** (no R/Julia in the authoring environment). Python exports are verified to reproduce VierStation’s results. The star multiple alignment is not ClustalO/MAFFT quality for divergent sets – use a dedicated aligner for publication.
* **ChEMBL is slow (15–25 s/call) and BindingDB intermittently unavailable**; both degrade to a warning with partial results. BindingDB and PDB ligands are never inferred to be “inhibitors”; only curated ChEMBL mechanisms and IC50 measurements use that word.
* Gene discovery from a raw sequence relies on NCBI BLAST (1–3 min); proteins from sequences use BLASTP search only to find a UniProt entry. No local protein-folding, by design.
* PDB ligand discovery reads the entries UniProt lists (best 6 by resolution); a co-crystallised ligand is reported as *observed*, which does not by itself show function. Ions and common crystallisation additives are filtered by a fixed list.
* Search-by-name for chemicals/genes returns top hits only; no cross-species ortholog logic.
* Single-process, single-user local server (SQLite). Multi-user sharing, cloud sync and roles were removed on purpose; to hand work to someone else, export a `.vsws` workspace file. The Docker image is **not verified** (no Docker daemon in the authoring environment).
* **Explorer limits.** Layout runs on the browser’s main thread (fine for the bounded ≤ 3,000-node views; no worker); above ~320 nodes the force layout is replaced by the faster concentric one. Cytoscape 3.30 crashes on parallel edges between *rounded* polygons, so node shapes avoid them. Restore/import are tested through the API (backup → change → restore, export → damage → import, a bad file is refused) but not under a running large job queue. No 3-D viewer for chemicals and no 2-D drawing of a chemical without a PubChem CID / InChIKey / SMILES (no chemistry toolkit is bundled; nothing is drawn rather than guessed). Protein images are backbone traces, not the 3-D viewer. PubChem and AlphaFold image **downloads are tested with scripted responses only**, not against the live services; the live Nominatim geocoder is still untested. Shapes and colours were checked with automated contrast and hue tests and screenshots – **no formal screen-reader or colour-vision-deficiency audit** (table mode and keyboard navigation are the text alternatives). Cloud sync is not implemented (not required).
* Accessibility: keyboard navigation, labels, landmarks and focus styles are implemented, but no formal screen-reader audit was done (the explorer’s table mode and keyboard navigation are the text alternative to the canvas).
